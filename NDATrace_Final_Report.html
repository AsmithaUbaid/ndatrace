1. The decision problem

NDATrace is a reviewer aid for enterprise legal operations. The primary user is a legal operations analyst who must check whether a signed or draft NDA satisfies a standard confidentiality requirement — a judgement that depends on paraphrases, definitions, exceptions, and cross-references, not a keyword match. The system returns a label (Entailment, Contradiction, or Not Mentioned) together with the specific source evidence the analyst can verify. The human reviewer remains the final authority on every case.

NDATrace does not give legal advice, does not autonomously approve or reject an agreement, and does not negotiate. Benchmarking uses ContractNLI (Koreeda & Manning, Findings of EMNLP 2021)[1], a proxy dataset of real NDAs annotated for exactly this task — not a complete enterprise legal playbook, and not a substitute for a firm's own precedent library.

2. Every rung had to earn its complexity

I built the system as a ladder, cheapest first, and required each additional layer to justify its quality, cost, latency, and new failure modes before it could stay.

Figure 1. Architecture ladder — each rung's status is the decision this report defends, not a survey of alternatives.

Rules were kept only as the non-AI floor: they are essentially free but cannot reason over paraphrase or exception language, which this task requires. FULL-context reasoning was added next because the dataset's documents are short enough (median 1,836 tokens) that a context-window limit was never the binding constraint — the open question was whether the hosted model reasoned well enough, not whether it could fit the document. RAG followed to bound cost and attach clause-level provenance to every answer. The agent was the last rung tried, and it did not survive contact with the evidence (§7). More autonomy was not retained unless it produced measurable value.

Figure 3. Recall@5 (bar length) and MRR@5 (label) before and after cross-encoder reranking, same 4,371-case population (E06).

Before reranking, the three candidate generators genuinely differed — hybrid led on both recall and MRR. After the identical cross-encoder reranker was applied to all three, they converged almost completely: a paired case-by-case check against the frozen BM25+reranker configuration agreed on 4,370 of 4,371 cases, with no evidence of a real difference. I retained BM25 + cross-encoder reranking by parsimony — the simplest generator that performs equally well — not because BM25 is statistically superior. The cross-encoder, not a more elaborate candidate generator, did most of the discriminating work.

A right label backed by unsupported evidence is not a successful result for a legal-review assistant.

Paired McNemar tests on the same 2,091 cases: classification accuracy difference p = 0.217 (not significant — RAG is not shown to be less accurate, nor FULL more accurate). Joint difference p = 0.0047 (significant — FULL's evidence-grounded advantage is real). FULL is the strongest measured benchmark configuration on this dataset; RAG's classification quality is statistically indistinguishable but its Joint rate is measurably lower, while it cuts classifier input tokens by roughly half. FULL remains the benchmark reference; RAG is retained as the prototype runtime.

6. Why RAG still powers the prototype

RAG was not selected because it wins the benchmark — it does not. It was selected because its operating properties fit the reviewer workflow: a bounded context regardless of document length, a per-document retrieval index reusable across all 17 standard requirements, and clause-level provenance attached to every answer, which makes reviewer spot-checking faster. This is a product-operability trade-off, not a benchmark-quality win, and this dataset's document lengths are too short to itself validate a claim that RAG scales better on 50–100 page contracts. RAG was selected for the interactive prototype because its bounded evidence path better fits reviewer workflow, accepting the measured Joint trade-off.

7. Why the agent was rejected

I tested whether giving the RAG path read-only investigation tools (search clauses, find defined terms, search exceptions, retrieve more evidence, inspect neighbouring clauses) could recover its failures on a fixed 150-case sample (E09–E11).

Table 2. Base RAG vs. two agent controller versions, same 150-case sample.
ConfigurationJointCases using ≥1 tool
Base RAG75.3%—
Agent V173.3%1.3%
Agent V2 (stronger controller prompt)68.7%20.0%

V1's controller almost never used its tools. Rewriting the controller prompt (V2) raised tool use fifteen-fold, but produced no useful tool-mediated recoveries — Joint fell further. The tool surface was deliberately bounded throughout (read-only tools, max 3 steps, max 2 tool calls, a 60-second wall-clock cap, a $0.01 per-escalated-case cost circuit breaker, duplicate-call protection), so the negative result is not an artifact of an unconstrained agent running wild. The tested selective retrieval-agent configuration did not earn its added complexity — this is a finding about the tested design, not a claim that agentic architectures are generally ineffective.

8. Failure analysis changed the next decision

Table 3. RAG's 576 non-Joint outcomes on the full 2,091-case TEST set, by cause (E20).
Failure categoryCases
Reasoning / classification448
Evidence selection59
Retrieval-limited55
Runtime / parser / source validity14

Most of RAG's residual failures are reasoning failures, not retrieval failures — retrieval-limited cases are a small minority of the 576. Since the retrieval design was already at its converged ceiling (§4), adding more retrieval actions or agent-style investigation loops would have targeted the smaller failure category, not the larger one. This is a second, independent line of evidence supporting the agent rejection in §7. Further retrieval complexity was not the next highest-value intervention.

9. Cost-to-serve, not API price

RAG's raw inference cost is lower than FULL's. But raw API price is not cost-to-serve. Under the modeled formula C_total = C_AI + (1 − p_joint) × C_H — where every non-Joint case falls back to human review at a modeled $3.33/case (5 minutes at $40/hour) — E20's own cost-to-serve computation gives:

Figure 4. Modeled all-in cost-to-serve per requirement check, AI inference plus the modeled human-fallback share of non-Joint cases (E20 cost_to_serve_comparison, E18 §7).

Both fall far below manual-only review, but FULL's all-in cost is modeled as lower than RAG's: RAG's ~17% lower raw API cost is outweighed by its 2.2-point lower Joint rate feeding more cases into the much larger modeled human-review cost. If NDATrace reviewed 500 NDAs a year at 17 requirement checks each (8,500 checks/year), that per-case gap compounds — a figure I flag as modeled, not realized: NDATrace has no verified enterprise human-review cost, and C_H is an explicit scenario assumption. The cheapest model call is not necessarily the cheapest system.

No agent, no automatic confidence router, and no silent FULL fallback run in this path (docs/architecture.md).

The project's strongest finding is not that one architecture wins every metric. It is that evidence-grounded review requires measuring the label and the evidence together, and that additional architectural complexity should be retained only when it improves that joint outcome enough to justify its cost and failure surface.
